## 一、当前结论

本阶段以“固定必修 Training 任务”为首个开发场景。按照当前 PRD，一期任务范围就是 10 个必修任务，重点不是继续讨论任务是否纳入一期，而是把这些任务的完整流程和不同完成类型跑通，并优先接入真实课程素材；没有真实素材的部分继续使用明确标注的 Mock 占位。

当前教师端已具备可点击原型基础：

- 三个独立板块：首页概览、今日任务、成长路径 / My TIT。
- 通用任务详情页，可承载不同任务完成方式。
- 10 个首期建议必修任务的三阶段展示。
- 学习小测、学习清单、上传审核、设备检测、外部培训 / 标签回传五种任务类型。
- 任务状态变化、首页/今日任务/成长路径进度同步、中英文切换。
- PC 端和 390px 移动端适配，以及 Toki 的欢迎、学习、等待、失败恢复和完成反馈。

下一阶段重点是：确认真实任务素材和完成规则，完善任务流程，验证所有任务类型的通用框架，并为后续数据/任务中心接入预留清晰的数据结构。

## 二、本阶段目标

### 2.1 目标

1. 以固定必修 Training 任务为主线，跑通“查看任务 → 进入详情 → 完成操作 → 状态更新 → 进度同步”的闭环。
2. 用同一套任务详情框架覆盖五种任务完成方式，避免每种任务单独开发一套页面。
3. 优先替换真实可用的课程、题目、上传说明、检测入口和培训链接；暂时没有的内容使用 Mock，并明确标注。
4. 保留后续接入任务中心和真实数据所需的前端字段、状态和结果展示位置。
5. 保证教师端表达专业、清晰、鼓励式成长，不展示未经确认的扣分、风险、投诉判定和正式毕业结论。

### 2.2 本阶段不做

- 不开发数据底座、Full Monitor、规则引擎和真实任务触发逻辑。
- 不开发运营后台、人工审核后台、申诉后台和 AI 知识库问答。
- 不确认或实现正式的 40 分制、毕业线、优秀线、延长观察和退出规则。
- 不把 Mock 的任务顺序、任务分类、日期、分数和完成结果写成正式业务规则。
- 不扩展到原生 iOS / Android App、主 App 嵌入和正式上线发布。

## 三、首个开发场景

### 3.1 主演示路径

```text
今日任务首页
  → 选择 Platform Policies
  → 进入通用任务详情
  → 查看真实视频/图文素材
  → 完成小测
  → 达到配置的 Mock 通过标准
  → 任务变为已完成
  → Toki 给出完成反馈
  → 首页、今日任务、成长路径和 My TIT 同步更新
```

Platform Policies 作为首个主演示任务；其他固定必修任务用于覆盖不同完成方式、状态和阶段解锁。10 个任务属于当前一期范围，但每项任务的正式分类、内容和完成规则仍需业务/培训确认。

| Day 1-7 | Device & Network Check | 外部设备检测 | 跳转入口、检测结果、重新检测 |

## 四、教师端开发内容

### 4.1 页面与路由

- 今日任务首页：展示 Day X/30、1 个首要任务、最多 2 个次要任务、截止提示、Toki 建议和成长路径入口。
- 成长路径：展示三段 Mock 阶段、10 个任务、前后顺序、已完成记录、后续阶段预览和阶段解锁。
- My TIT：展示试用期位置、任务完成进度、下一里程碑、准备状态、能力标签和当前优先任务。
- 通用任务详情：固定展示 Why / How / Result、预计用时、截止提示、完成标准、帮助入口和主要操作。

### 4.2 通用任务详情框架

所有任务共用以下结构：

1. 任务标题、阶段、状态和任务标签。
2. 为什么收到这个任务。
3. 老师需要怎么做。
4. 预计用时、截止提示和注意事项。
5. 真实素材或 Mock 占位。
6. 完成标准。
7. 完成后会发生什么。
8. 帮助/规则入口和 Toki 提示。
9. 根据任务类型切换具体操作容器。

### 4.3 五种任务流程

| 类型 | 流程 | 需要确认的关键内容 |
|---|---|---|
| 学习小测 | 开始学习 → 查看素材 → 开始小测 → 提交 → 通过或重试 | 素材、题目、通过标准、重试规则 |
| 学习清单 | 开始学习 → 查看步骤 → 逐项确认 → 完成 | 清单内容、是否允许跳过、完成标准 |
| 上传审核 | 查看要求 → 选择文件 → 提交 → 审核中 → 通过或需要更新 | 文件格式、大小、时长、审核状态和反馈 |
| 外部设备检测 | 查看说明 → 开始检测/跳转 → 返回结果 → 通过或重新检测 | 检测入口、返回方式、结果状态、失败处理 |
| 外部培训/标签回传 | 查看培训说明 → 前往平台 → 完成学习 → 同步结果 → 获得标签 | 平台链接、完成回传方式、标签名称和同步时机 |

### 4.4 教师端状态

本期统一使用容易理解的教师端状态：

- 待完成：Start
- 进行中：Continue
- 已提交/审核中：Under review
- 已完成：Done
- 未通过/需要更新：Try again / Update required
- 逾期：Overdue

后台的“待触发、系统校验、人工复核、已豁免”等状态不直接展示给老师。

### 4.5 数据预留范围

本阶段不做真实数据接入，但前端需要保留后续接入所需的 Mock 契约，至少包括：

- `task_id`、`task_name`、`stage`、`task_type`。
- `completion_method`、`trigger_reason`、`priority`、`due_time`。
- `status`、`complete_standard`、`result_message`。
- `help_link`、`estimated_duration`、`unlock_condition`。
- `review_status`、`appeal_type`、`recovery_path`。
- `toki_state`、`toki_message`、`celebration_type`。
- `material_url`、`quiz_id`、`external_url` 等真实素材接入字段。

以上字段只是前端契约草案，不代表后端接口已经确认。数据、规则和任务下发仍由相关系统负责人确认。

## 五、真实素材接入计划

### 5.1 优先接入顺序

1. Platform Policies：视频/图文、字幕或文稿、5 道小测题、通过和重试文案。
2. Lesson Preparation / TTP Orientation：学习材料和清单内容。
3. Profile & Credentials Completion：上传示例、格式限制、提交说明和审核结果示例。
4. Device & Network Check：检测入口、检测说明、通过和需要修复示例。
5. Cocos、SET：培训平台入口、完成状态和能力标签示例；Free Trial 资料仅作为 Domestic pending 候选保留。
6. 全部任务的正式中英文名称、按钮、帮助入口和联系支持方式。

### 5.2 素材使用原则

- 已提供并确认可用的真实素材直接接入。
- 尚未提供的素材使用清晰占位，并标注 `Mock`，不伪造正式链接或正式业务内容。
- 真实课程素材、题库、审核规则和外部平台链接必须经过业务/培训负责人确认后再写入页面。
- Logo 和 Toki 只使用已确认的官方素材，不自行绘制或改造。

## 七、需要业务/培训澄清的问题

以下问题均来自当前 PRD 的“内容与业务待确认”部分。任务范围已经确定为当前 PRD 中的 10 个必修任务，本节不再讨论是否纳入一期，而是逐项确认任务应该如何设计和落地。

当前已确定：

- 一期范围按当前 PRD 的 10 个必修任务执行。
- 开发场景先选择固定必修 Training 任务。
- 以 Platform Policies 作为首个主路径，其他任务用于覆盖不同类型和状态。
- 数据先做前端字段和 Mock 契约预留，暂不把真实数据接入作为本阶段前端交付前提。

### 7.1 业务与内容问题

| 问题 | 需要明确的结果 |
|---|---|
| 每个任务的正式业务属性 | 确认毕业必修、优秀加分、普通提醒的分类；未确认前统一标 Mock |
| 30 天从哪个节点开始计算 | 确认 Launch、激活、首课或其他起算节点 |
| 阶段名称是否正式 | 确认 Day 1-7、Day 8-14、Day 15-30 的正式名称和阶段目标 |
| 每个任务何时截止 | 确认具体日期、首课前/周期内等截止口径 |
| 如何算完成 | 确认小测分数、清单确认、上传审核、设备检测和培训标签的完成标准 |
| 真实素材是否已有 | 确认视频、文档、题目、图片、上传示例和外部平台链接 |
| 正式中英文文案是否已有 | 确认任务名、Why / How / Result、按钮、状态和帮助文案 |

每个任务至少需要业务/培训补齐：任务目的、适用对象、前置条件、操作步骤、完成标准、完成收益、失败处理、素材入口和负责人。

### 7.2 五类任务流程问题

这一部分需要业务/培训逐项确认“内容怎么设计、老师怎么操作、什么结果算完成”，前端再据此落成统一详情页流程。

- 学习小测：学习材料是什么；小测题目和答案是什么；通过分数是多少；是否允许重试；答错后展示什么解释和补学内容。
- 学习清单：清单由哪些步骤组成；是否必须全部勾选；是否可以中途退出；是否允许回看或修改；全部确认后是否立即完成。
- 上传审核：上传什么内容；合格示例是什么；允许的格式、大小、时长是什么；提交后由谁审核；审核中如何提示；需要更新时展示什么原因和修改建议。
- 外部设备检测：检测哪些设备和指标；检测入口是什么；如何跳转和返回；哪些结果算通过；失败后是重新检测、查看指南还是联系支持。
- 外部培训/标签回传：培训平台入口是什么；需要完成哪些课程/步骤；完成状态如何同步；标签名称是什么；同步延迟或失败时教师端如何提示。

建议按“任务一张确认卡”逐项收集，不建议只确认任务名称和链接后直接开发页面。

### 7.3 前端与后续系统衔接问题

- 任务最终由哪个系统下发和维护状态。
- 教师端提交的结果需要回传哪些字段。
- 哪些任务结果由系统校验，哪些需要人工复核。
- 状态更新是实时回传、轮询还是重新进入页面时刷新。
- `task_id`、任务类型、完成方式、状态、结果和素材链接等字段是否采用统一命名。
- 后续接入真实数据时，教师端需要消费哪些数据，哪些内部字段不能展示给老师。

## 八、建议的确认流程

```text
确认任务清单与顺序
  → 确认每项任务的完成标准
  → 确认真实素材与外部入口
  → 确认中英文文案和教师端状态
  → 前端接入素材并完成流程
  → 业务/培训负责人逐项验收
  → 再确认任务中心字段、状态回写和后续真实数据联调
```

每项任务建议形成一张最小确认卡：

| 字段 | 内容 |
|---|---|
| 任务名称 | 中文名 / 英文名 |
| 所属阶段 | Day 1-7 / Day 8-14 / Day 15-30 或正式阶段名 |
| 任务类型 | 学习小测 / 学习清单 / 上传审核 / 设备检测 / 外部培训 |
| 为什么做 | 教师可理解的一句话 |
| 怎么完成 | 操作步骤和入口 |
| 完成标准 | 系统/人工如何确认 |
| 完成收益 | 任务完成后页面如何反馈 |
| 素材链接 | 视频、文档、题目、图片、平台链接 |
| 失败处理 | 重试、重新上传、重新检测或联系支持 |
| 负责人 | 业务、培训、审核或系统负责人 |

- [ ] 至少一个学习小测任务接入真实素材；没有真实素材的任务明确标注 Mock。
- [ ] 上传审核、设备检测、外部培训和标签回传均有可演示的流程状态。
- [ ] 任务完成后，今日任务、成长路径和 My TIT 的任务状态/进度同步变化。
- [ ] 待完成、进行中、审核中、已完成、需要更新/未通过、逾期状态均有示例。
- [ ] 中英文切换覆盖三板块、任务详情和核心操作文案。
- [ ] Toki 覆盖欢迎、学习、等待、失败恢复和完成庆祝五类节点。
- [ ] PC 和 390px 移动端无横向溢出、遮挡或关键操作不可见。
- [ ] 所有正式业务口径、真实素材和真实链接均有来源或负责人，不把 Mock 当成已确认规则。
