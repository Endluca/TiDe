# 任务触发中心：任务体系与下发/回流契约 V1

版本：V1.0
日期：2026-07-16
面向对象：任务触发中心、老师端任务体验、运营端、数据与联调同事
状态：可作为 Mock 开发与跨团队接口评审基线；正式发布前仍需补齐素材链接、外部系统能力和业务验收

## 0. 这份契约解决什么

这不是老师端页面 PRD，也不是任务列表说明。

它冻结五件事：

1. 什么条件下可以产生任务；
2. 任务触发中心向老师端交付什么；
3. 老师完成任务后必须回传什么；
4. 哪个系统对哪一段状态拥有唯一写权。
5. 哪些结果是老师任务，哪些其实是运营 Case、系统动作请求或通知意图。

核心边界：

> 任务发出后的交互可以由老师端同事负责，但不能成为数据断点。没有执行结果回流，触发中心就无法去重、重开、结算新师任务分、安排下一任务或判断毕业。

## 1. 冻结的责任边界

### 1.1 单一写入方

| 对象/字段 | 唯一写入方 | 其他系统能做什么 |
| --- | --- | --- |
| 任务模板、模板版本、适用范围 | 任务触发中心配置域 | 只读消费 |
| 触发事实、内部原因、证据关联 | 任务触发中心 | 老师端不可见、不可改 |
| `task_id`、下发版本、优先级、排序、截止时间 | 任务触发中心 | 展示并回执；不能重建 ID 或自行改序 |
| 老师可见标题、Why、How、完成标准 | 已发布模板 | 老师端按语言渲染；不能让 Agent 或前端自由改写 |
| 查看、开始、提交、重试等执行状态 | 老师端任务运行域 | 任务触发中心消费事件并建立只读投影 |
| 自动/人工/外部校验结果 | 被指定的验证方 | 老师端展示映射结果；触发中心消费事件 |
| 人工确认事实、投诉 valid 结果 | 运营复核域 | 触发中心在确认后继续路由 |
| 五维积分、毕业状态 | 确定性计分/毕业引擎 | 其他系统只读，不直接加分或毕业 |

禁止两个系统同时直接修改同一运行字段。跨域变化通过版本化命令与事件完成。

### 1.2 各方交付

任务触发中心负责：

- 从标准事实中识别信号；
- 执行 DIRECT / AGENT / MANUAL 路由；
- 从已发布模板创建任务；
- 决定 `is_primary`、`display_rank`、优先级、截止时间和依赖；
- 输出老师安全投影；
- 记录下发、修订、撤回和回执；
- 消费执行结果，支持去重、后续触发、积分和效果回看。

老师端同事负责：

- 今日任务、成长路径、详情页和完成反馈体验；
- 六类完成容器的交互；其中前五类来自老师端 PRD，`CONFIRMATION_FORM` 来自最新业务补充；
- 查看、开始、提交、重试、求助、复核申请；
- 上传、测验、设备检测、外部培训跳转或同步；
- 产生标准化执行事件；
- 将验证结果映射为老师可理解的状态。

老师端不能：

- 自行创建业务任务；
- 自行复制一个新的 `task_id`；
- 自行调整任务优先级或顺序；
- 直接修改积分、毕业、投诉有效性或内部风险事实；
- 把 Toki 做成可自由创造任务的聊天 Agent。

## 2. 五个不能混用的分类字段

### 2.1 `output_type`：触发中心到底产出什么

| 枚举 | 含义 | 例子 |
| --- | --- | --- |
| `TEACHER_TASK` | 老师需要完成的行动 | 必修培训、设备重测、首课缺席 Yes/No 确认 |
| `OPS_REVIEW_CASE` | 运营需要确认事实或处理争议 | 投诉 valid、假早退、睡觉、申诉 |
| `SYSTEM_ACTION_REQUEST` | 请求外部系统执行有副作用的动作 | 释放后续课程、加入项目池 |
| `DELIVERY_INTENT` | 请求触达系统发送已批准内容 | 邮件、站内信、短信/WhatsApp 提醒 |

任务触发中心可以规划这四类结果，但权限不同：`TEACHER_TASK` 在策略范围内可自动下发；`OPS_REVIEW_CASE` 自动进入人工队列；有外部副作用的 `SYSTEM_ACTION_REQUEST` 在授权规则未冻结前必须人工确认；`DELIVERY_INTENT` 只发送模板化内容，不允许 Agent 自由写消息。

### 2.2 `task_category`：为什么产生

| 枚举 | 含义 | 默认受众 | 是否可计新师任务分 |
| --- | --- | --- | --- |
| `MANDATORY_GROWTH` | 按入职/阶段节点必须完成的成长任务 | TEACHER | 仅配置为计分的固定任务 |
| `PERSONALIZED_IMPROVEMENT` | 已确认短板对应的改进任务 | TEACHER | 否 |
| `MANUAL_REVIEW` | 需要运营确认事实或争议 | OPS | 否 |
| `OPS_INTERVENTION` | 运营跟进、跨系统处理或升级 | OPS | 否 |

### 2.3 `completion_method`：老师如何完成

前五类与老师端 PRD 保持一致；最新业务补充新增了首课缺席后的结构化 Yes/No 回复，因此需要第六类：

| 枚举 | 老师端能力 | 最小配置 |
| --- | --- | --- |
| `QUIZ` | 学习后答题 | `content_ref`、`quiz_id`、通过线、尝试次数 |
| `CHECKLIST` | 阅读或逐项确认 | `items[]`、必选项、提交规则 |
| `UPLOAD_REVIEW` | 上传资料并等待审核 | 文件类型/数量/大小、审核说明、重提规则 |
| `DEVICE_CHECK` | 打开外部检测并等待结果 | provider、启动入口、回调关联、重测规则 |
| `EXTERNAL_SYNC` | 前往外部培训/平台并等待标签或状态同步 | 外部对象、入口、同步频率、超时说明 |
| `CONFIRMATION_FORM` | 对单一业务问题提交结构化选项 | `question_id`、批准的选项、答复时限、后果说明 |

`task_category` 与 `completion_method` 必须分开。例如“设备整改”属于 `PERSONALIZED_IMPROVEMENT`，完成方式是 `DEVICE_CHECK`；“TESOL 必修”属于 `MANDATORY_GROWTH`，完成方式可能是 `EXTERNAL_SYNC` 或 `UPLOAD_REVIEW`。

### 2.4 `verification_mode`：谁确认完成

- `SYSTEM_IMMEDIATE`：任务内确定性校验；
- `SYSTEM_ASYNC`：外部检测/标签异步回传；
- `HUMAN_REVIEW`：人工审核；
- `BEHAVIOR_OBSERVATION`：后续真实课堂或供给事实达到条件；
- `HYBRID`：先完成学习/整改，再等待真实行为验证。

### 2.5 `audience`：给谁看

- `TEACHER`：可进入老师端；
- `OPS`：只进入运营队列；
- `INTERNAL`：只用于系统编排，不对人展示。

人工确认和运营干预不能因为名称中带“任务”就误发给老师。

## 3. 任务生命周期

### 3.1 下发生命周期，由触发中心写

`SCHEDULED → READY → ISSUED → ACKNOWLEDGED`

异常或变更：

- `REJECTED`：老师端无法接收，必须带错误码；
- `REVISION_PENDING`：优先级、截止时间或公开内容版本待同步；
- `WITHDRAWN`：触发事实失效或人工撤回，历史保留。

只有 `ACKNOWLEDGED` 才表示老师端运行域已经接管，不等于老师已看到。

### 3.2 执行生命周期，由老师端运行域写

`AVAILABLE → VIEWED → STARTED → SUBMITTED → VERIFYING → COMPLETED`

分支状态：

- `RETRY_REQUIRED`：可以修改后再提交；
- `FAILED_FINAL`：达到最大尝试次数或不可继续；
- `WAIVED`：经授权无需继续；
- `EXPIRED`：超过可执行窗口且不再允许提交；
- `CANCELLED_BY_WITHDRAWAL`：收到任务触发中心的撤回命令。

逾期是独立字段 `due_status=ON_TIME/OVERDUE`，不能覆盖执行状态。一个任务可以同时是 `SUBMITTED + OVERDUE`。

### 3.3 老师端展示映射

| 执行状态 | 老师端英文 | 允许的主要动作 |
| --- | --- | --- |
| AVAILABLE | Start | VIEW、START |
| VIEWED | Start | START |
| STARTED | Continue | CONTINUE、SUBMIT |
| SUBMITTED / VERIFYING | Under review | VIEW |
| COMPLETED | Done | VIEW_RESULT |
| RETRY_REQUIRED | Try again / Update required | RETRY、SUBMIT、REQUEST_REVIEW |
| WAIVED | Not required | VIEW_RESULT |
| EXPIRED | Overdue / Contact support | REQUEST_HELP |
| CANCELLED_BY_WITHDRAWAL，未查看 | 隐藏 | 无 |
| CANCELLED_BY_WITHDRAWAL，已查看 | Not required | VIEW_RESULT |

老师端不得直接提交一个新 `status`。它只能发送动作命令，由运行域校验后变更状态。

模板在任务发出时形成不可变快照。之后修改模板，只影响新任务；历史任务仍能还原老师当时看到的内容和规则。

固定必修成长任务维度总计 30 分。正式单项分值未确认前，由世文按同一计分版本和当前 10 项正式清单平均分配；本契约不再维护另一套固定分值或积分包。

规则：

- 只有固定必修任务首次完成时产生一次确定结果；页面步骤拆分、重试和重复回调不得重复计分；
- 当前清单版本固定为 10 项；内容待补充的 NT-M04 在正式版本发布前不得伪造完成结果；
- 个性化整改、人工确认、运营干预不计新师任务分；
- `EXEMPTION_CONFIRMED` 表示用等价证据证明能力，可满足积分包；`WAIVED_OPS` 只是运营豁免，默认不满足毕业也不加分；
- 任务适用范围、豁免和正式单项分值仍以世文返回的计分版本为准；教师端不自行调整分母。

| ID | 受众 | 触发场景 | 运营需要确认/执行 | 输出 |
| --- | --- | --- | --- | --- |
| MANUAL-01 | OPS | 任意投诉 | valid / invalid / pending、分类、Level、老师责任、证据 | 标准事实或关闭；VALID 后再路由 |
| MANUAL-02 | OPS | 拉黑 | 是否为老师原因、样本和关联投诉 | VALID/INVALID/观察 |
| MANUAL-03 | OPS | 重大差评或低样本强负向 | 是否代表真实问题 | 后续任务或观察 |
| MANUAL-04 | OPS | 假早退 | 进出记录、互动、回放和例外 | VALID/INVALID |
| MANUAL-05 | OPS | 睡觉疑似 | 回放、时长、回应情况 | VALID/INVALID |
| MANUAL-06 | OPS | 设备/网络责任争议 | 平台、地区网络、设备和检测误差 | VALID/豁免/重测 |
| MANUAL-07 | OPS | 多来源冲突、teacher/lesson 归属不清 | 修复归属或隔离数据 | 可用事实或数据异常 |
| MANUAL-08 | OPS | 老师申诉/重测争议 | 原证据、新材料、规则版本 | 维持/推翻/补证据 |
| MANUAL-09 | OPS | Level 0/1、私联、代课、严重态度等高风险 | 事实有效性与后续业务动作 | 风险结论和授权动作 |
| OPS-C01 | OPS | 新师首课缺席回复 No、超时未回复或需要运营确认 | 确认老师意图、已预约课程范围、学员通知和释放权限 | 保留、继续观察或生成课程释放请求 |
| OPS-C02 | OPS | 未登录、未激活、下发无法到达 | 联系信息和账号问题 | 恢复访问或关闭 |
| OPS-C03 | OPS | 无 slots/无课且原因不清 | 是否老师原因、平台供给问题 | 任务/豁免/数据修正 |
| OPS-C04 | OPS | 多次逾期、连续验证失败 | 是否需要帮助、延期、撤回或升级 | 运营动作 |
| OPS-C05 | OPS | 毕业条件满足但有未决事实/数据异常 | 清理阻塞项 | 解除或继续阻塞 |

首课缺席后先由 `NT-R04` 获取结构化 Yes/No。回复 Yes：保留后续课程并继续可靠性复训/观察；回复 No：生成 `OPS-C01`，再形成 `SYSTEM_ACTION_REQUEST=COURSE_RELEASE_REQUESTED`；未回复：升级 `OPS-C01` 并按模板产生二次 `DELIVERY_INTENT`。没有明确跨系统权限、释放范围、回滚和学员通知规则前，Agent 不得直接执行课程释放。

## 8. 触发与编排规则

### 8.1 三种路由

- `DIRECT`：固定节点或单一确定信号对应固定模板；
- `AGENT`：多信号冲突、同根因合并、顺序、优先级和最小任务组合；
- `MANUAL`：投诉、拉黑、假早退、睡觉、重大差评、争议和高风险行为。

### 8.2 Agent 自主范围

Agent 从启用第一天即可自主执行：

- `CREATE_FROM_TEMPLATE`；
- `MERGE_EVIDENCE`；
- `REPRIORITIZE`；
- `REVISE_DUE_AT`，但只能在模板范围内；
- `REMIND`；
- `ESCALATE_TO_OPS`；
- `REOPEN`；
- `WITHDRAW`；
- `NO_ACTION`。

Agent 不得发明模板、任务文案、素材、完成标准、分数、毕业规则或事实；不得绕过人工确认。

### 8.3 当前任务排序

任务触发中心必须输出排序结果，不让老师端二次编排：

1. 已确认、必须立即处理的安全/履约问题；
2. 临近截止且阻塞首课或毕业的必修任务；
3. 设备和账号等执行前置任务；
4. 可靠性、课堂质量和反馈改进；
5. 产能提升；
6. 非阻塞的成长任务。

约束：

- 当前任务最多 3 个；
- 恰好 1 个 `is_primary=true`；
- 同时进行的个性化任务最多 2 个；
- MANUAL/OPS 任务不占老师端名额；
- 预览任务进入 `task_roadmap`，不等于已下发、不可执行；
- P0 内部风险不得把敏感原因直接显示给老师。

### 8.4 去重与重开

默认 `dedupe_key`：

```text
teacher_id + template_id + root_cause_code + trigger_window
```

- 冷却期内新信号只合并 `evidence_id`；
- 只有模板、根因和关闭条件都兼容时才能合并；
- 已完成任务在冷却期后复发，可创建新 `task_id` 并关联 `previous_task_id`；
- 同一提交/回调重复到达不得重复完成、重复积分或重复触发；
- 数据纠错导致信号失效时，未查看任务可撤回；已查看任务显示中性历史，不静默删除。

## 10. 老师动作与结果回流合同

### 10.1 老师动作命令

老师端至少支持：

- `VIEW_TASK`；
- `START_TASK`；
- `SUBMIT_TASK`；
- `RETRY_TASK`；
- `REQUEST_HELP`；
- `REQUEST_REVIEW`；
- `RESPOND_CONFIRMATION`。

每条命令必须带：

```text
event_id / idempotency_key
task_id
expected_task_version
actor_id
occurred_at
payload
```

`RESPOND_CONFIRMATION` 只能提交模板批准的 option code，不能用自由文本替代 Yes/No。老师端不得直接 `PATCH status`。

### 10.2 运行事件 `task.runtime_event.v1`

```json
{
  "event_id": "evt_uuid",
  "event_type": "task.runtime_event.v1",
  "idempotency_key": "runtime:task_uuid:sequence_8",
  "task_id": "task_uuid",
  "task_version": 1,
  "runtime_sequence": 8,
  "runtime_status": "COMPLETED",
  "verification_result": "PASSED",
  "actor_type": "EXTERNAL_SYSTEM",
  "actor_id": "device_check_provider",
  "occurred_at": "2026-07-16T03:00:00Z",
  "payload": {
    "attempt_no": 2,
    "result_ref": "safe_result_reference",
    "completed_at": "2026-07-16T03:00:00Z"
  }
}
```

验证事件至少区分：

- `VERIFICATION_PASSED`；
- `VERIFICATION_RETRY_REQUIRED`；
- `VERIFICATION_REJECTED`；
- `EXTERNAL_COMPLETION_SYNCED`；
- `HUMAN_REVIEW_COMPLETED`；
- `WAIVER_APPROVED`。

处理规则：

- `event_id` 全局幂等；
- `runtime_sequence` 对同一任务单调递增；
- 旧 `task_version` 的事件不能覆盖新版本；
- 乱序事件可暂存，但不能倒退业务状态；
- `COMPLETED` 只有验证通过后成立；
- 计分引擎只消费已验证完成事件；
- 老师端删除或重建页面数据不得导致历史事件丢失。

### 10.3 回流到教师宽表的任务指标

| 字段 | V1 统一口径 |
| --- | --- |
| `prob_task_total_cnt` | 统计窗口内被老师端 `ACKNOWLEDGED` 的任务实例数 |
| `prob_task_completed_cnt` | `VERIFICATION_PASSED` 的任务实例数；提交不算完成 |
| `prob_task_required_cnt` | `is_required=true` 且适用于该老师的任务实例数 |
| `prob_task_required_completed_cnt` | required 且 `VERIFICATION_PASSED` |
| `prob_task_overdue_cnt` | `as_of` 时仍未进入终态且 `due_at < as_of` 的任务数 |
| `prob_task_rectify_cnt` | `task_category=PERSONALIZED_IMPROVEMENT` 且 `is_rectification=true` |
| `prob_task_rectify_completed_cnt` | 上述整改任务中 `VERIFICATION_PASSED` 的数量 |
| `prob_task_rectify_closed_loop_rate` | `effect_status=IMPROVED` 的整改任务数 / 已进入效果观察的整改任务数 |

建议新增：

- `prob_task_ever_overdue_cnt`：窗口内曾逾期过的任务数；
- `prob_task_verified_pass_cnt`：所有验证通过数；
- `prob_task_rectify_effective_cnt`：真实效果改善数；
- `prob_task_last_event_at`；
- `prob_task_data_as_of`。

否则“老师做完动作”“提交物通过”和“真实课堂改善”会被混成同一个完成率。

## 11. 修订与撤回

触发中心可以发送：

- `task.reprioritized.v1`；
- `task.due_date_revised.v1`；
- `task.content_revision_available.v1`；
- `task.withdrawn.v1`。

每次修订使 `task_version + 1`。老师端必须回 `ACK`。已提交任务原则上不改完成标准；确需变更时应撤回旧任务并新建任务，避免老师按旧标准提交却被新规则拒绝。

## 12. 成长路径投影

老师端需要两个不同接口/投影：

### `current_tasks`

- 只包含已下发且当前可行动任务；
- 最多 3 个；
- 带唯一排序和允许动作。

### `task_roadmap`

- 展示阶段、已完成、当前和预览任务；
- 预览来自适用的任务计划，不一定已有 `task_id`；
- 预览项不能被开始或提交；
- 真正解锁时由触发中心创建任务实例。

## 13. Mock 与联调验收

### 13.1 Teacher Contract Sandbox

如果老师端正式页面尚未接好，只做内部 Sandbox，不做第二套生产老师端：

- 展示 1 个主任务和最多 2 个次任务；
- 渲染六种 `completion_method` 的 Mock JSON；
- 模拟 Start、Continue、Under review、Done、Try again、Overdue；
- 发送动作命令和验证结果；
- 验证下发、回执、幂等、版本和状态映射。

### 13.2 必过用例

1. 同一 `task.issued` 重放两次，只创建一个运行任务；
2. 老师端不支持某完成方式，明确拒绝且触发中心进入异常队列；
3. 老师端不能自行改 `priority/display_rank`；
4. 同一提交回调两次，只完成和加分一次；
5. 旧版本回调不能覆盖新版本；
6. 已查看任务撤回后保留中性历史；
7. 投诉未 VALID 时，老师端收不到处罚性任务；
8. 一个老师当前任务最多 3 个，个性化任务最多 2 个；
9. 必修任务验证通过后，积分只结算一次；
10. 个性化整改完成不直接加新师任务分；
11. 外部同步超时显示等待状态，不伪造完成；
12. `PENDING/SOURCE_ERROR/DISPUTED` 证据不能产生负向老师任务；
13. 敏感内部原因在老师接口响应中为零泄漏；
14. Sandbox 完整跑通下发→查看→提交→验证→回流→积分/下一任务；
15. 下游中断恢复后可按事件重放，不产生重复任务或重复积分。

### 13.3 建议时效

- 下发回执：正常情况下 60 秒内；
- 老师动作事件：交互完成后 1 分钟内；
- 系统即时验证：5 分钟内；
- 外部标签/培训同步：按来源 SLA，响应中必须给预计同步时间；
- 人工审核：由任务模板配置 SLA；
- 超时不等于失败，进入异常/等待队列并保留原状态。

## 14. 老师端同事开始设计前需要拿到的包

1. 本契约；
2. 首批模板 JSON 与中英文内容；
3. 六类 `action_schema` 示例；
4. `current_tasks` 和 `task_roadmap` Mock；

老师端视觉和交互可以独立设计，但只要这十项不变，两边就能并行开发而不互相等待。

## 15. 当前未阻塞开发、但上线前必须确认

- Self-intro、TESOL、ME Culture/PARSNIP 的最终毕业硬门槛；
- 真实素材链接、Quiz、培训标签和外部系统 owner；
- 设备内存检测值 `7000` 的单位与来源字段；
- 投诉二/三级分类的正式中英文版本与 valid 责任人；
- 首课缺席后的课程释放范围、授权、回滚和学员通知；
- 各人工审核 SLA、申诉和豁免权限；
- 老师端是否展示精确积分。后端保留字段，首版可用功能开关展示成长进度。

这些事项不妨碍用 Mock 开工，但未确认前，对应模板不得从 `DRAFT` 发布到生产。

## 16. 来源对照

- 业务补充文档：积分成长、红线、人工确认、设备阈值、出席定义、任务候选和逐课计分；冲突时优先采用该文档。
- 老师端页面 PRD：今日任务数量、成长路径、既有五类操作容器、老师展示状态、公开原因和 Mock 接入要求；最新业务补充要求额外支持首课缺席确认表单。
- 教师宽表字段表：任务聚合指标和五维候选字段；任务字段由本系统下发及下游回流后生成，不是已有原始数据。
