# 教师端任务设计交接 v2（更新于 2026-07-21）

> 交接对象：负责教师端既有固定任务，以及“接收我方触发任务 → 执行动作 → 返回任务状态”的教师端同事。
>
> 本文区分两套链路：`G01`–`G10` 是教师端已有固定成长任务，我方只接收完成事件；`S01`–`S05` 与 23 个 `P-*` 是我方可能下发的 28 类个性化改善任务。触发阈值、证据计算、运营 Case、通知、推荐和课程动作由任务触发中心负责。28 个下发任务全部为 0 分。

## 1. 双方边界

双方有两个方向：

- **方向 A——28 类个性化改善任务**：任务触发中心发送 `teacher_dispatch_payload`，其中包含稳定模板编码、标题、具体触发原因 `why`、动作摘要、完成标准、收益、优先级和截止时间。教师端负责把这些内容做成可执行体验，并以我方 `assignment_id` 回传状态；回传只更新任务状态，不结分；
- **方向 B——10 个固定成长任务**：教师端继续使用已有任务系统持有、展示并校验 `G01`–`G10`。任务触发中心不发送这些任务，不生成 `assignment_id`，只接收教师端的可信完成事件并按服务端积分配置幂等结分。

教师端不需要接收或解释内部 SQL、来源表、学生 ID、投诉原文、内部定责或处罚建议。具体事实值、窗口和阈值以每次下发的 `why/evidence_summary` 为准，不应写死在页面文案里。

接口与状态细节见 [教师端任务下发与状态回传接口 v2](../contracts/教师端任务下发与状态回传接口_v2.md)。

当前文档用于本地 Mock 契约验证和教师端方案设计交接；可信 DerivedSignal、真实教师业务时区、鉴权及端到端联调完成前，28 类任务的真实发布保持关闭。固定必修完成事件的本地 API 已实现，但仍受运营账号鉴权保护且未完成 Provider 验签，不能表述为教师端已经接通。

## 2. 共同规则与差异

- 对 28 类下发任务，`SUBMITTED` 只表示已提交；教师端完成模板规定的可信校验后才回 `COMPLETED + VERIFIED_COMPLETED`。所有状态事件都只更新任务状态，任务完成也不结分。
- 对 10 个固定必修任务，我方不接收过程状态，只接收 `COMPLETED + VERIFIED_COMPLETED + result_version=1`；事件不含 `assignment_id`。
- 首课继续授课确认是唯一有业务分支的任务：老师选择后回 `COMPLETED + CAN_CONTINUE/CANNOT_CONTINUE`，截止未答复回 `EXPIRED + EXPIRED_BY_POLICY`。`CANNOT_CONTINUE` 或 `EXPIRED` 都只会让触发中心创建待人工确认的课程释放请求与 P0 运营 Case，不代表课程已释放。
- 人工复核类任务提交后进入 `UNDER_REVIEW`，运营关闭复核后才回 `COMPLETED`；批准例外使用 `WAIVED`。
- 任务完成和后续表现改善是两件事。后续课程是否改善由触发中心观察，不应长期卡住教师端任务。
- 固定成长事件 V1 不带 camp，按同一教师、同一 `task_code` 终身只结分一次；28 个下发任务全部 0 分。供给 10 分由我方内部根据教师维度统计快照首次满足 `peak_slot_cnt >= 40` 自动达成并永久锁定，不走任务下发或状态回传。分值由我方服务端配置，教师端不得上报分数或资格结果。
- 重新打开 28 类触发任务必须生成新的 assignment；教师端不得改写已完成任务的历史状态。固定必修任务的误报完成也不得覆盖原事件，应走独立的数据修正流程。

## 3. 教师端已有固定成长任务（10 个，合计 30 分）

下表用于双方对齐稳定 `task_code` 和可信完成含义，不是我方下发模板清单。教师端已有任务的页面、阶段和执行入口保持由教师端系统管理；我方不会发布 `TR-G01`–`TR-G10`。

| ID / 标题 | 教师端动作 | `COMPLETED` 的可信条件 | 分值 |
|---|---|---|---:|
| `G01` Profile & Credentials Completion | 完成 Self-intro、注册所需 Web App 资料，并提交全部资质证明 | 所有必填资料齐全，配置的 AI/人工审核通过 | 4 |
| `G02` Device & Network Check | 进入可信检测入口，检测电脑、网络、麦克风、扬声器和摄像头；按结果整改 | 可信检测结果为 PASS | 3 |
| `G03` Platform Policies | 学习平台规则与合规内容，完成知识检查 | 必修内容已查看，配置的小测或确认通过 | 3 |
| `G04` Lesson Preparation | 完成备课清单、教材查看和课前设置 | 所有必填清单项均由教师端确认 | 3 |
| `G05` TTP Orientation | 完成 TTP 入门内容和清单 | 所有必修 TTP 入门项完成 | 1 |
| `G06` ME Culture & PARSNIP | 学习文化与敏感边界内容，完成小测/确认 | 必修内容完成且知识检查通过 | 2 |
| `G07` Reliability Training | 学习履约、出席、迟到与早退规则并完成小测 | 培训完成且知识检查通过 | 2 |

| `G09` Cocos Course Training | 在指定培训入口完成 Cocos 课程 | 可信培训系统返回有效 Cocos 完成标签 | 10 |

前四项用于计算首推准备资格，但触发中心本身不控制流量。10 项全部完成才形成 30 分固定成长任务分；供给里程碑分不能补固定成长任务缺口。教师端只上报完成事实，不能在事件中上报上述分值、累计分、毕业或金牌结果。固定成长完成事件 V1 不接收 `WAIVED`；批准例外若需要影响资格或积分，必须另行确认业务规则和升级接口，不能伪装成 `COMPLETED`。

## 4. 我方下发：供给主题的个性化改善任务（5 个，全部 0 分）

| ID / 标题 | 教师端动作 | `COMPLETED` 的可信条件 | 分值 |
|---|---|---|---:|
| `S01` Open Your First Slots | 在未来 7 天开放至少 5 个有效教学 slots | 可信供给快照确认未来 7 天有效 slots ≥5；平台/请假例外回 `WAIVED` | 0 |
| `S02` Open Peak Teaching Slots | 补开未来 7 天 Peak slots | 可信供给快照确认未来 7 天 Peak slots ≥10 | 0 |
| `S03` Open TTP Priority Slots | TTP 资格有效时补开 TTP slots | 资格有效且未来 7 天 TTP slots ≥5 | 0 |
| `S04` Active Days Challenge | 把未来 7 天的有效 slots 分布到至少 3 天 | 可信供给快照确认有效开放天数 ≥3 | 0 |
| `S05` Valid Completion Challenge | 保持足够开放量并可靠完成已分配课程 | Day 10 后滚动 7 天有效完课 ≥5，且不存在平台供给例外 | 0 |

S01–S05 的回传只改变 assignment 状态并支持后续效果观察，不产生积分流水。唯一供给积分规则是我方内部教师维度统计快照 `peak_slot_cnt >= 40`：首次达到后自动加 10 分并永久锁定，后续下降或数据纠错都不撤分；纠错只保留前后值和审计。该里程碑不生成教师任务、publication 或 assignment；教师端不需要新增模板或接口字段。该业务口径已在积分 v4 中实现并通过本地回测，不代表教师端真实联调已经完成。

## 6. 28 类下发任务中教师端需要设计的内容

教师端可自行决定 28 个下发模板采用清单、小测、上传、设备检测、外链学习或受控选择，但必须满足：

- 机器结果能映射到本文的 `COMPLETED` 条件；
- 每次回传使用稳定 `result_code/result_version`；当前所有模板共用全局 `result_contract v1`，仅接受 `result_version=1`，不要求教师端为触发中心提供逐模板 JSON Schema；
- 不允许由教师自由文本直接触发课程释放、处罚或资格变化；
- 支持 `SUBMITTED → UNDER_REVIEW → COMPLETED/FAILED/WAIVED`；
- 保留 assignment、模板编码和回调事件的幂等关系。

教师端完成方案设计后，双方只需逐模板确认三件事：执行入口、可信校验来源、状态/结果码映射。触发阈值不属于教师端设计范围。

## 7. 固定必修完成事件交接

固定必修事件与 28 类任务的 assignment 回调是两份接口：

- 当前本地路径：`POST /api/v2/fixed-task-status-events`；另有 `/api/v2/fixed-task-instances` 供运营查询完成镜像；正式 Provider 网关路径仍可在联调时调整；
- 不携带 `assignment_id`，必填字段为 `provider_event_id / source_system / external_task_id / teacher_id / task_code / status / occurred_at / sequence / result_code / result_version / signature`；`result_payload` 可省略；
- `task_code` 只允许 `G01`–`G10`，`status` 首版只接受 `COMPLETED`，`result_code` 固定为 `VERIFIED_COMPLETED`，`result_version` 固定为整数 `1`；
- `provider_event_id` 在所有来源中全局唯一并用于幂等；`source_system + external_task_id` 首次绑定教师和任务编码后不可变；
- `result_payload` 只放可选的受控 `verification_code / artifact_refs`，不能放 metrics、分数、累计分、毕业/金牌结论或驱动动作的自由文本；
- 产品已确认不存在复营或跨营期回补。V1 不接收 camp 字段，按 `teacher_id + task_code` 终身最多结分一次；若未来业务边界反转，必须新建合同版本并加入明确 camp identifier；
- `signature` 当前只做必填校验并保存 SHA-256，没有验真；当前外部联调继续暂停。正式开放前必须完成 Provider 鉴权、真实验签、防重放、重试、回读、计分对账和异常修正演练。

完整字段解释与示例见 [教师端任务下发与状态回传接口 v2](../contracts/教师端任务下发与状态回传接口_v2.md) 第 6 节。
