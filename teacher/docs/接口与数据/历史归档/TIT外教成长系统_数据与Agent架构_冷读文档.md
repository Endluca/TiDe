# TIT 外教成长系统：数据、Agent 与任务触发机制

> 文档类型：冷读版
> 适用读者：运营负责人、业务负责人、产品及跨端协作同事
> 阅读目标：不依赖现场讲解，理解系统解决什么问题、数据如何处理、Agent 实际负责什么、任务如何触发，以及当前版本能用到什么程度
> 当前口径：v0.3 本地混合试跑版，2026 年 7 月

---

## 一、先说结论

这不是一个单纯的积分看板，也不是一个让大模型自动给老师“派活”的系统。

它要解决的是：**如何把分散的课堂、教师、用户反馈和任务执行数据，持续转化为可解释、可执行、可复盘的教师成长干预。**

整个系统遵循五个原则：

1. **目标不是提高出营率，而是缩短新师达到“稳定合格供给”的时间。**
   老师达到分数线只是阶段结果，最终还要看出营后 30 / 60 / 90 天能否持续稳定履约、保持课堂质量并获得用户认可。

2. **数据不会直接交给 Agent。**
   原始数据先经过标准化、来源标记、积分计算和信号生成，Agent 只处理已经结构化的教师状态与合法动作。

3. **Agent 不是自由任务生成器。**
   新任务只能来自已发布模板；Agent 的核心能力是处理多信号、多任务和已有任务状态之间的优先级与生命周期编排。

4. **任务完成不等于老师已经改善。**
   完成任务只更新任务事实；是否真正改善，要由后续课堂数据重新证明。

5. **当前最大的业务能力缺口，不是模型不够聪明，而是“指标如何稳定变成标准信号”。**
   真实宽表已经可以计分，但正式 lesson 增量、部分指标来源和真实教师的标准信号生成仍需补齐。

## 二、系统负责什么，不负责什么

### 2.1 本系统负责

- 接收教师、课堂、用户反馈和任务执行数据；
- 计算五维积分、出营状态、金牌状态和风险状态；
- 把指标变化转成可审计的标准信号；
- 制定、触发和分发教师任务；
- 管理任务模板、触发规则、积分规则、Agent 策略和投递策略；
- 接收教师端回传的任务状态；
- 为运营提供教师 360、任务中心、运营 Case、输出中心和审计能力；
- 评估一次任务干预是否改善了后续课堂表现。

### 2.2 教师端协作系统负责

老师从“收到任务”到“完成任务”之间的正式体验，由教师端协作同事负责，包括：

- 任务展示；
- 开始、继续、提交和完成操作；
- 表单、测验、材料提交等具体执行组件；
- 任务执行状态和结果回传。

本系统通过任务写入接口把任务发给教师端；教师端通过状态接口把 ACK、开始、提交、完成、失败或求助等事件回传。

### 2.3 明确不由 Agent 直接决定

- 自由发明新任务；
- 自由修改任务文案、参数和截止时间；
- 直接修改教师积分；
- 决定出营、淘汰或投诉最终定责；
- 直接释放课程或执行其他高风险外部动作；
- 用一次低样本课堂直接形成处罚性结论。

## 三、数据如何一步步变成任务

系统的数据链路可以概括为：

> 原始事实 → 标准化 → 五维指标 → 教师状态 → 标准信号 → 任务编排 → 对外输出 → 效果复盘

### 3.1 原始事实层

系统需要四类输入：

| 数据类别 | 主要内容 | 当前状态 |
| --- | --- | --- |
| 教师 30 天宽表 | 完课、Peak 完课、迟到、早退、好评、收藏、15 日复约等教师级累计数据 | 已接入 1065 位真实 / 混合教师 |
| Lesson 级事实 | 每节课的履约、用户反馈、投诉、设备网络和课堂质量证据 | 正式增量数据待接入，部分使用 Mock |
| 任务执行事件 | ACK、开始、提交、验证、完成、失败、求助、复核 | 合同已冻结，当前由 Sandbox 模拟 |
| 运营配置 | 积分、出营门槛、任务模板、冷却期、Agent 和投递策略 | 已有版本化配置页面 |

### 3.2 标准化与数据治理

数据进入系统后，不直接覆盖成一个“最终数字”，而是保留完整来源：

1. **保留原始快照**
   记录导入文件摘要、批次、原始字段、原始值、行号和规则版本。同一批次的历史快照不可被后续修正覆盖。

2. **统一业务语义**
   对齐 Teacher ID、Lesson ID、时间、时区、课程状态和枚举含义，解决不同来源中同一概念命名不一致的问题。

3. **标记数据来源**
   每个指标都要说明它是真实事实、确定性派生、Mock、模拟还是代理值。

4. **保留证据状态**
   没有证据时，对应分数按规则记 0；但系统仍要保留“没有证据”“来源异常”“有争议”等状态，不能把它们全部压成同一种 0 分。

这一步的目的，是确保运营看到任何分数、信号或任务时，都能追溯到：**它为什么出现、依据是什么、用了哪一版规则。**

## 四、五维指标怎样计算

教师成长使用五个独立维度积分，再累加为 raw 总分：

```text
raw 总分
= 可靠性分
+ 用户反馈分
+ 课堂质量分
+ 产能分
+ 新师任务分
```

其中，可靠性、用户反馈和课堂质量的目标模型是按每节课分别结算；产能和新师任务按教师状态、供给或任务事件结算。

| 维度 | 当前试跑口径 | 当前来源边界 |
| --- | --- | --- |
| 可靠性 | 准时完课 × 2 + Peak 完课 × 1；迟到、早退、真实缺席另做硬门槛或红线 | 真实字段 + 确定性派生 |
| 用户反馈 | 好评 × 5 + 收藏 × 5 + 15 日复约 × 8 | 真实字段 |
| 课堂质量 | 无问题课程 × 2 | 当前按真实完课量 × 80% 模拟 |
| 产能 | 当前基础分 10 | Mock，后续接开放 slots、重点时段 slots 和真实完课量 |
| 新师任务 | 当前基础分 30 | Mock，后续由可信任务完成与验证事件驱动 |

### 4.1 出营不是只看总分

当前出营需要同时满足：

- raw 总分 ≥ 100；
- 基础分 ≥ 30；
- 30 天完课量 ≥ 10；
- 用户反馈分 > 0；
- 可靠性分 > 0；
- 没有严重红线。

全部条件满足后立即出营，不再额外等待固定时间。

### 4.2 金牌同样包含硬门槛

当前金牌需要同时满足：

- raw 总分 ≥ 660；
- 已满足全部出营资格；
- 基础分 ≥ 40；
- 用户反馈分 ≥ 20；
- 迟到 ≤ 1；
- 早退 = 0；
- 真实缺席 = 0。

真实宽表回算中，550 位教师达到出营分数线，但只有 538 位同时满足最终出营条件；108 位达到金牌分数线，但只有 23 位满足最终金牌条件。

这个差异说明：**总分只能反映累计表现，不能替代单维底线和风险门槛。**

当前课堂质量、产能、新师任务、严重红线和真实缺席拆分仍包含 Mock 或代理输入，因此现阶段资格结果只用于规则试跑，不能直接作为正式人事结论。

## 五、指标如何变成标准信号

积分本身不会直接触发任务。系统还需要判断“这个状态是否值得干预”。

标准信号由四层分析组成：

### 5.1 差距分析：离目标还有多远

- 距离出营总分线还有多少；
- 哪个单维门槛尚未满足；
- 课量是否不足；
- 是否触发迟到、早退、缺席等红线。

硬门槛不能被其他维度的高分抵消。

### 5.2 趋势分析：正在改善还是持续恶化

系统比较最近 N 节课或最近 7 天与上一窗口：

- 差距持续缩小：改善；
- 多个窗口没有变化：持平；
- 负向事件持续增加：恶化。

这样可以减少单节课偶然波动造成的误触发。

### 5.3 严重度分析：现在是否紧急

优先级顺序为：

> 红线事件 > 单维硬门槛 > 普通分数差距

普通差距还要结合剩余 Camp Day、差距大小、连续发生次数和证据可信度，形成 P0–P3 等级。

### 5.4 可行动性分析：是否存在安全的干预手段

即使信号有效，也不一定立即发任务。系统还要检查：

- 是否有已发布且适用的任务模板；
- 是否处于冷却期；
- 是否已存在同类任务；
- 是否与当前主任务冲突；
- 是否需要人工确认；
- 当前教师是否还有可行动任务槽位。

一条完整标准信号至少应包含：

```text
signal_id + teacher_id + dimension + code + severity
+ current_value + threshold + window
+ evidence_status + evidence_refs
+ source_version + occurred_at + expires_at
```

标准信号是指标系统和任务系统之间的正式契约。没有这一层，Agent 只能看到分散数字，无法稳定、可审计地编排任务。

## 六、Agent 实际做什么

### 6.1 Agent 不是“从模板里随便挑一个”

服务端会先根据教师状态完成以下工作：

1. 读取有效信号和已有任务；
2. 按适用范围、证据状态、Camp Day、冷却期等规则筛选模板；
3. 生成一份合法动作目录；
4. 固定每个动作的对象、参数、原因码和 `action_id`；
5. 再把最小决策包交给 Agent。

Agent 最终返回的是一个或多个 `selected_action_ids`，不是自由文本，也不是完整任务内容。

### 6.2 什么时候调用 Agent

- **DIRECT**：只有一个明确候选、且没有历史任务时，系统按确定性规则直接执行，不调用模型；
- **AGENT**：存在多个候选，或老师已经有历史任务时，由 Agent 做优先级和生命周期编排；
- **MANUAL**：运营从已发布模板人工签发，或处理必须保留人工确认的高风险事项。

### 6.3 Agent 能选择哪些动作

| 动作 | 含义 |
| --- | --- |
| `CREATE_FROM_TEMPLATE` | 从已发布模板创建任务 |
| `MERGE_EVIDENCE` | 把新证据合并进进行中的同类任务 |
| `REOPEN` | 问题再次发生且冷却期结束后重开任务 |
| `REPRIORITIZE` | 根据新风险调整任务优先级和主次顺序 |
| `REVISE_DUE_AT` | 在安全边界内缩短截止时间 |
| `REMIND` | 生成临期提醒 |
| `ESCALATE_TO_OPS` | 创建运营 Case，不直接执行高风险动作 |
| `WITHDRAW` | 触发事实失效且任务未开始时撤回 |
| `NO_ACTION` | 当前没有必要或没有安全动作可执行 |

结构化输出允许同时选择多个动作。新建任务最多一项主任务和两项次任务，最终还要遵守老师当前任务槽位和个性化改善任务数量限制。

### 6.4 Agent 的判断重点

在合法动作范围内，Agent 主要比较：

- 哪个信号风险最高；
- 哪个动作时间最紧；
- 是否与已有任务重复或冲突；
- 是新建任务，还是合并证据、提醒、升级或撤回更合适；
- 老师当前的任务负担是否过高。

因此，当前 Agent 的准确定位是：

> **受约束的任务生命周期编排器，而不是原始数据分析师，也不是自由任务创作者。**

模型超时、限流、拒绝或输出不合法时，系统会拒绝模型结果并使用确定性策略降级，不让任务触发链路中断。

## 七、任务如何触发，系统输出什么

### 7.1 五类重新评估触发源

| 触发源 | 示例 |
| --- | --- |
| Lesson 事件 | 完课、迟到、早退、缺席、反馈、投诉、质量异常 |
| 指标跨线 | 低于单维门槛、达到出营线、风险等级变化 |
| 时间窗口 | Camp Day、临期、逾期、冷却期结束 |
| 风险与数据 | 红线、证据冲突、数据缺失、来源修正 |
| 运营配置 | 模板发布、阈值版本变化、人工确认结果 |

这些事件触发的是“重新评估”，不等于每次都创建新任务。系统可能选择合并、提醒、升级、撤回或不处理。

### 7.2 四类业务输出

| 输出类型 | 用途 |
| --- | --- |
| `TEACHER_TASK` | 发给教师端的任务 |
| `OPS_REVIEW_CASE` | 需要运营处理的 Case |
| `SYSTEM_ACTION_REQUEST` | 需要人工审批或外部系统执行的动作请求 |
| `DELIVERY_INTENT` | 站内通知、小提醒和其他投递意图 |

Provider 调用记录属于 Agent 调试信息，不属于业务输出。

输出中心需要展示完整因果链：

```text
教师
→ 来源事件
→ 指标快照
→ 标准信号
→ 匹配模板
→ 合法动作目录
→ Agent 选择
→ 投递结果
→ 外部任务 ID
→ 状态回传
→ 效果观察窗口
```

这让运营不仅能看到“系统发了什么”，还能回答“为什么发、依据是什么、是否真正送达、后来有没有效果”。

## 八、跨系统闭环如何运行

完整链路分为五步：

1. **本系统触发任务**
   生成任务写入请求、合同版本和幂等键。

2. **教师端接收并落库**
   返回外部任务 ID 和接收结果。只有消费方回执，才能证明任务真正被接收。

3. **教师执行任务**
   教师端负责 ACK、开始、提交、完成、失败或求助等过程。

4. **状态回传本系统**
   教师端调用任务状态写入接口，本系统更新任务事实、运营队列和后续动作。

5. **用后续课堂验证效果**
   重新计算五维指标和标准信号，判断同类问题是否减少。

关键边界是：

> **任务完成只证明动作完成；教师成长必须由后续课堂事实证明。**

新师任务维度可以根据可信完成事件计分，但它不能替代可靠性、用户反馈和课堂质量的实际改善。

## 九、运营和负责人应该看哪些指标

### 9.1 北极星指标

**新师达到稳定合格供给所需时间。**

它比单纯出营率更可靠，因为降低规则门槛也能提高出营率，却不一定增加真正稳定的好老师。

### 9.2 业务结果指标

- 平均出营时间；
- 出营资格率和金牌资格率；
- 出营后 30 / 60 / 90 天稳定履约率；
- 课堂质量和用户反馈保持情况；
- 出营后重新跌破关键门槛的比例。

### 9.3 干预效率指标

- 信号触发量和有效触发率；
- 任务接收、开始、完成和逾期率；
- 重复触发率；
- 运营介入率；
- 任务完成后同类信号减少率；
- 不同任务模板的后续改善效果。

### 9.4 数据健康指标

- 核心字段覆盖率和缺失率；
- 数据延迟和修正率；
- 证据可回查率；
- 真实、派生、Mock 和代理数据占比；
- 不同规则版本下的重算差异。

## 十、当前已经做到什么

当前 v0.3 已具备一套可持续本地试跑的 Web App：

- PostgreSQL 持久化和 Alembic 迁移；
- 登录、RBAC 和配置中心；
- 1065 位真实 / 混合教师宽表导入与计分投影；
- 教师 360、运营行动台、任务中心和人工任务发布；

- Teacher Contract Sandbox，用于跨端合同验证；

它目前适合：

- 运营内部试用；
- 积分和触发规则校准；
- 任务模板及输出调试；
- 跨端合同准备；
- 真实数据与 Mock 边界验证。

## 十一、当前还不能被描述成什么

当前版本不能被描述为“已经生产上线”或“已完成真实端到端联调”，原因包括：

1. 正式 lesson 增量数据和部分关键指标事实源尚未接入；
2. 真实导入教师尚未稳定生成完整标准信号；
3. 真实教师缺少可信 IANA 时区，任务签发当前安全关闭；
4. 正式教师端接口、鉴权和测试环境尚未完成消费方联调；
5. 站内通知、提醒、审批和外部动作目前主要记录意图或模拟回执；
6. 当前后端固定单 API 进程，尚未完成多 Worker 并发安全改造；
7. 正式部署、监控告警、备份恢复和回滚演练尚未建立；
8. 受 Mock 或代理输入影响的出营和金牌结果不能作为正式人事结论。

## 十二、下一阶段最重要的工作

### 12.1 补齐“指标 → 标准信号”

这是任务自动触发能否真正工作的核心。需要冻结：

- 信号代码；
- 计算窗口；
- 差距和趋势规则；
- 严重度等级；
- 证据要求；
- 有效期和失效规则；
- 无任务模板时的处理方式。

### 12.2 接入 lesson 增量与缺失维度

重点补齐：

- 课堂质量；
- 真实缺席、请假和系统取消拆分；
- 严重红线；
- 新师任务可信完成事件；
- 产能和重点时段供给；
- 历史数据修正与重算机制。

### 12.3 完成教师端真实联调

逐项验证：

- 任务写入；
- ACK；
- 站内通知；
- 六类任务 Action；
- Submission；
- Runtime Event；
- 错误码、幂等、乱序和重试。

### 12.4 建立真实投递与生产运行能力

- 补齐可信教师时区；
- 建设通知、提醒、审批和外部动作 Worker；
- 改造事务型 Repository 和并发控制；
- 建设正式部署、账号生命周期、监控、备份和回滚。

### 12.5 用后续表现校准规则

真正有效的任务，不是完成率最高的任务，而是能让同类信号减少、并提高出营后稳定性的任务。

因此，后续需要按任务模板持续比较：

- 触发前后的指标变化；
- 同类问题是否复发；
- 对不同类型教师是否同样有效；
- 是否产生过多打扰或运营负担；
- 是否需要调整模板、阈值、冷却期或优先级。

---

## 十三、最终要形成的能力

这个系统最终不是把所有运营判断交给大模型，而是把低风险、规则明确的干预自动化，并让需要人工判断的事项拥有更稳定的事实基础和执行闭环：

> 老师始终知道下一步应该做什么、为什么收到这个任务、做完会发生什么；
> 运营始终知道现在最需要介入谁、依据是什么、应该采取什么动作；
> 负责人始终能判断任务体系是否真的缩短了新师成长时间，而不是只提高了表面的出营率。

这也是数据、Agent、任务中心和两个看板必须围绕同一套事实与指标运行的原因。
