# 新师训练营协作开发标准

> 适用对象：Echo、嘉荷，以及双方使用的 AI。  
> 当前集成基线：`version2`。`main` 是较早版本，不作为新代码的开发基线。  
> 本文约束代码职责和日常协作；如进入正式上线流程，另按公司上线规范执行。

## 0. 启用条件

- 本文默认不自动生效。只有 Echo 在当前任务中明确要求“按公司规范”或“按协作规范”时，才按本文执行。
- 一次任务中启用本文，不代表后续任务继续自动启用。
- 未明确启用时，以 Echo 当前任务中的直接指令为准，不强制从 `version2` 新建分支，也不自动执行本文的分支、评审或合入流程。

## 1. 核心原则

1. Echo 负责整体架构、公共能力、通用任务引擎、Tasks 容器及非任务功能。
2. 嘉荷主要负责已分配的固定必修任务和个性化任务的内容、配置、任务内交互与专属规则。
3. 为了减少彼此代码冲突，公共架构统一由 Echo 维护。嘉荷需要公共能力时，可以先和 Echo 沟通，由 Echo 提供扩展点或接口。
4. 双方都从独立功能分支开发，完成代码评审后再合入 `version2`；不直接向 `main` 或 `version2` 提交功能代码。
5. 事实还没有确认时，请标记为 Mock，暂不补充为正式规则。

## 2. 协作分工

| 范围 | Echo | 嘉荷 |
| --- | --- | --- |
| 路由、页面骨架、目录结构 | 负责 | 由 Echo 统一维护 |
| 全局状态、数据流、接口层、存储方案 | 负责 | 由 Echo 统一维护 |
| 公共组件、通用任务框架、设计系统 | 负责 | 直接使用，调整前先沟通 |
| 全局样式、主题、响应式规则 | 负责 | 由 Echo 统一维护 |
| 构建配置、依赖、脚本、锁文件 | 负责 | 由 Echo 统一维护 |
| 数据库结构、接口契约、世文对接 | 负责 | 由 Echo 统一维护 |
| 已分配的固定必修和个性化任务内容与配置 | 提供规范和接口 | 负责 |
| 已分配任务的专属步骤、题目、校验和完成规则 | 评审 | 负责 |
| 已分配任务的专属素材和局部样式 | 评审 | 负责 |
| My TIDE、Tasks 页面骨架、成长路径、任务排序和跨入口实例 | 负责 | 使用 Echo 提供的任务接入点 |

“任务内交互”只指某个固定必修或个性化任务自身的步骤、题目、清单、上传项、提示和专属完成规则，不包括改造通用任务引擎。

### 2.1 任务配置与公共能力的边界

- 凡 Echo 已提供配置模型支持的视频、原生文档、小测、清单、上传和拍照任务，嘉荷可直接配置任务内容、素材、步骤顺序、题目答案、通过标准、重试规则和教师文案。
- Echo 负责通用任务引擎、全局状态机、跨任务数据结构、账号权限、世文接口契约和公共存储方案，不需要亲自实现每个任务的专属功能。
- 拍照检测等任务可以作为任务专属功能整体交给嘉荷，包括任务内的摄像头授权、拍摄、预览、重拍、上传、专属校验、异常处理、相关后端扩展和测试。
- 嘉荷在任务单已授权的前后端隔离目录内可直接完成这类功能，不要求 Echo 预先开发；Echo 只在代码评审时检查公共边界。
- 任务需要改动全局路由、通用状态机、公共存储方案、账号权限、数据库公共结构、世文接口或公共依赖时，再按例外流程说明影响，不得在任务分支中自行改动。
- 本文所说的“配置”是项目内的已发布任务配置，不是新建运营或规则配置后台。

### 2.2 任务 UI 一致性规范

- 任务外层统一使用 Echo 提供的任务页容器、顶部导航、返回逻辑、标题区、状态、进度、帮助入口和结果区；嘉荷主要负责任务内部工作区。
- 任务内部必须复用项目已有的字体、颜色变量、间距、圆角、阴影、按钮、表单、卡片、状态和反馈样式；不在任务中另建一套视觉系统。
- 任务专属样式必须限定在该任务根容器下，不修改 `:root`、`body`、全局标签、通用类名或公共组件样式。
- 拍照、视频和答题等任务可以有专属布局和操作状态，但页面层级、主次按钮、状态颜色、文案语气和退出方式必须与其他任务一致。
- 必须覆盖默认、加载、禁用、成功、未通过、权限拒绝和网络失败等实际会出现的状态，失败反馈继续使用鼓励式教师表达。
- 按钮和可点击控件需有明显的焦点状态，移动端可操作区域不小于 44×44px。
- 交付时同时提供 PC 和 390px 移动端主流程截图，与当前 Tasks 及通用任务详情页对照评审；不得出现横向溢出、遮挡、无法操作或风格明显割裂。

### 2.3 数据访问与接口边界

- 嘉荷负责的前端、任务配置和任务专属后端逻辑均不得直接连接本系统 PostgreSQL、世文 PostgreSQL、OSS、AI 网关或邮件服务。
- 固定任务和个性化任务统一通过 Echo 维护的公共任务接口读取任务上下文、保存进度、提交、查询验证结果和发起重试；前端不得自行拼接数据库字段。
- 个性化任务只使用公共接口返回的 `assignment_id / task_code / teacher_safe_reason / due_at / status` 等教师安全字段，不读取世文内部 publication、阈值、证据或风险字段。
- 任务如需积分、课程、训练营身份或通知，只能调用本系统后端提供的教师安全接口；由后端实时只读世文安全表或视图，并负责失败降级。
- 嘉荷不得自行新增或修改公共数据库字段、迁移脚本、公共 API、世文协议和跨系统状态；发现缺口时按 2.4 节提交扩展需求。
- Echo 提供 OpenAPI、TypeScript 类型和 Mock 示例作为开发合同。合同未实现前可以使用 Mock，但不得把 Mock 字段当成已确认的真实字段。
- 密码、令牌、数据库连接串、世文原始载荷、学生信息、图片和文件二进制不得写入任务配置、前端日志或接口示例。

### 2.4 数据与公共能力扩展流程

嘉荷发现现有合同不能完成任务时，在任务 PRD 或 PR/MR 中提供：

```text
任务编码：
使用场景：
缺少的输入或输出：
为什么现有字段不能表达：
期望的数据类型和是否必填：
是否涉及历史数据迁移：
期望的失败或空状态：
```

Echo 负责判断采用公共字段、任务扩展字段还是新接口，并统一更新数据库迁移、OpenAPI 和 TypeScript 类型。字段变更默认采用增量迁移；已有真实数据后不得直接删除或改写历史字段。

## 3. 任务级 PRD

每个固定必修任务及正式上线的个性化任务模板，在具体实现前先建立一份独立任务 PRD：

- 文档放在 `docs/PRD/必修任务/`；
- 从 `_必修任务PRD模板.md` 复制创建；模板同时支持固定必修和个性化任务；
- 在 `README.md` 任务索引中登记，并由总 PRD 关联；
- 嘉荷负责填写任务内容、流程、题目、素材、完成判定和验收用例；
- 只有任务需要越过默认隔离目录或改动公共能力时，才需要 Echo 确认数据边界和代码接入方式；
- 任务实现发生变化时，同步更新任务 PRD，尽量与代码放在同一个 PR/MR 中评审。

总 PRD 定义系统共性，任务 PRD 定义单个任务的个性化规则。两者存在冲突时，先记录差异并一起确认，暂不直接改写总 PRD。尚未确认的内容继续标记为 Mock 或“待确认”。

- [必修任务 PRD 索引](docs/PRD/必修任务/README.md)
- [必修任务 PRD 模板](docs/PRD/必修任务/_必修任务PRD模板.md)

## 4. 嘉荷的代码协作范围

嘉荷接入 `version2` 后，代码主要放在 Echo 提供的以下隔离目录中：

```text
frontend/src/features/task-content/**
frontend/src/data/tasks/**
frontend/public/assets/tasks/**
frontend/src/features/task-content/**/*.test.*
```

后端工程建立后，任务 PRD 明确授权的任务专属后端代码统一放在：

```text
backend/src/modules/task-extensions/<task-code>/**
backend/test/task-extensions/<task-code>/**
```

`backend/contracts/**`、`backend/database/**`、未来的 `backend/src/integrations/**` 和全部迁移脚本仍由 Echo 统一维护。`backend/` 已用于保存开工合同和数据库准备资产；业务源码将在后端开发开始后建立。

这些目录当前如尚未建立，可以先由 Echo 确定目录和接入接口。嘉荷及其 AI 等扩展点准备好后再接入，无需自行调整现有架构。如任务单同时授权任务专属后端目录，嘉荷可直接完成该任务前后端功能；公共存储、账号权限、全局数据结构和跨系统回传仍不在默认修改范围内。

任务索引或任务 PRD 中负责人已登记为“嘉荷”，且修改仅发生在上述默认隔离目录或已建立的任务专属后端目录时，视为已默认授权，不需要 Echo 逐个功能再确认。

任务开工信息应在任务索引、任务 PRD 或任务单中明确，不要求 Echo 逐项人工重复说明：

- 任务 ID 和任务名称；
- 任务类型、`template_version` 和 `execution_contract_version`；
- 现有配置模型是否能完整表达该任务；
- 允许修改的具体目录或文件；
- 可调用的公共组件和接口；
- 输入、输出、完成状态和验收标准；
- 业务内容是否为正式口径，还是 Mock。

任务单未写明的文件，默认不在嘉荷修改范围内。

## 5. 需要先和 Echo 确认的内容

以下内容由 Echo 统一维护。如任务确实涉及这些文件，嘉荷及其 AI 可以先说明原因，和 Echo 确认后再修改：

```text
frontend/src/App.jsx
frontend/src/main.jsx
frontend/src/components/**
frontend/src/i18n.jsx
frontend/src/*.css
frontend/package.json
frontend/pnpm-lock.yaml
frontend/scripts/**
backend/contracts/**
backend/database/**
AGENTS.md
COLLABORATION_STANDARD.md
*.sql
```

为了让双方代码更容易合并，也请尽量避免：

- 调整目录结构、路由、全局状态或公共数据结构；
- 新增、删除或升级依赖；
- 复制公共组件后另建一套相似架构；
- 修改其他任务来迁就当前任务；
- 自行定义世文接口、数据库字段或跨系统协议；
- 用整文件覆盖的方式解决冲突；
- 顺手格式化、重命名或清理职责外代码。

确实需要调整以上内容时，可以先写清“遇到的问题、期望的扩展点、涉及文件”，由 Echo 一起判断处理方式。确认后如需嘉荷修改，建议使用单独提交，方便评审和回退。

## 6. 分支标准

### 6.1 基线

- 当前统一以 `version2` 作为集成基线。
- `main` 用于保留旧版本历史，新的功能分支统一从 `version2` 创建。
- Echo 如变更集成基线，应先更新本文，再通知嘉荷。

### 6.2 分支命名

```text
echo/<功能名>
jiahe/task-<任务名>
```

一个分支尽量只承载一个任务或一组强相关配置，不混入架构调整和其他功能。

### 6.3 嘉荷从旧 `main` 迁移到 `version2`

1. 先把旧 `main` 上尚未保存的工作提交到独立备份分支，不继续直接在 `main` 开发。
2. 从最新 `version2` 新建 `jiahe/task-<任务名>`。
3. 为降低冲突，不建议把旧开发分支整体 merge 或 rebase 到 `version2`。
4. 按任务逐个迁移内容、素材、题目和规则；优先重新接入 Echo 提供的扩展点。
5. 旧代码如果依赖旧路由、旧公共组件或旧状态结构，只迁移业务意图，不照搬架构实现。
6. 缺少扩展点时，可以先保留该部分，由 Echo 补充公共能力后再继续。

## 7. 提交与合入

提交信息建议使用：

```text
feat(task-content): 配置平台规则任务
fix(task-content): 修正小测完成判定
content(task-content): 更新课程文案与素材
```

每次提交应满足：

- 只包含当前任务相关文件；
- 不包含构建产物、临时文件和无关格式化；
- 不提交真实账号、密钥、个人信息或生产数据；
- Mock 数据和正式数据有清楚标记。

合入步骤：

1. 功能分支先同步最新 `version2`。
2. 开发者完成自测，并检查修改文件是否都在授权范围内。
3. 发起合入 `version2` 的 PR/MR，由另一人评审。
4. 嘉荷的 PR/MR 由 Echo 协助检查架构边界后再合入。
5. 有冲突时由对应文件的负责人决定处理方式；架构文件冲突由 Echo 处理。
6. `version2` 和 `main` 统一通过评审后合入，不直接推送功能代码。

## 8. 验收标准

嘉荷交付一个固定必修或个性化任务时，至少验证：

- 为什么做、要做什么、怎么做、完成标准、完成后会发生什么均已展示；
- 步骤、题目、答案、校验和完成状态符合任务单；
- 个性化任务只展示世文已下发的教师安全原因，不展示积分收益，不自行触发或分配；
- 任务内部使用现有设计变量和公共组件，与 Tasks 及通用任务详情页风格一致；
- 失败反馈采用鼓励式表达，不出现运营内部风险语言；
- 正式口径未确认的分数、日期、结果和素材均标注 Mock；
- PC 与 390px 移动端无溢出、遮挡和不可操作区域；
- PC 与 390px 移动端主流程截图已与当前任务页基线对照评审；
- 不影响其他任务、My TIDE、成长路径和通用任务流程；
- 项目原有检查和构建通过。

## 9. AI 开工前检查

双方的 AI 每次修改代码前，请先完成以下检查：

1. 阅读根目录 `AGENTS.md`、本文，以及当前任务对应的任务 PRD。
2. 检查当前分支、工作区未提交文件和本次角色。
3. 确认开发基线为最新 `version2` 派生分支。
4. 列出计划修改的文件，并按本文判断是否有权限。
5. 发现他人未提交内容时保留原样，不覆盖、不删除。

如果 AI 的身份或文件范围不明确，默认先采用更小范围。嘉荷的 AI 如需修改默认协作范围之外的文件，请先保留这部分不动，说明原因并请 Echo 确认。

AI 完成后请汇报：

- 实际修改文件；
- 完成的任务规则；
- 自测结果；
- 是否涉及默认协作范围外的文件；
- 仍需 Echo 提供的扩展点或待确认业务口径。

## 10. 例外记录模板

如确需调整默认协作范围，可以在任务单或 PR/MR 中记录：

```text
例外原因：
涉及文件：
为什么需要调整任务隔离目录之外的内容：
拟采用方案：
影响范围与回退方式：
Echo 确认：是 / 否
```

“Echo 确认：是”填写完成后，再开始处理这部分修改。
